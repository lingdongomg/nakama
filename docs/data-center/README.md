## 规划总览

目标：以 Nakama 为参考实现，建设一套适配公司游戏场景的数据中心。分期如下，**分期依据是「数据可信度要求」而非功能多少**。

### 第一期：玩家数据（复用为主）

Nakama 已覆盖，重点是确定字段归属与写入权限。

- 账号与身份（多渠道登录）
- 玩家档案（昵称、头像、等级、经验、设置）
- 货币与资产余额
- 资产变动流水

详见 `01-nakama-baseline.md`。

### 第二期：对战数据上报（Nakama 不支持，需自建）

Nakama 只做实时对战（房间、同步、消息），**对局结果不落库**。这块必须自建，并且第一件事是决定权威模型：

- 服务端权威结算（推荐用于竞技/付费相关）
- 客户端上报 + 服务端回放校验（成本低，但有作弊面）
- 客户端上报 + 统计口径兜底（仅用于分析用途，不能驱动发奖）

### 第三期：关卡策略分析（自建，对标数数科技类产品）

需要事件模型 + 分析链路，产出漏斗、卡点、留存、行为序列。核心难点不在查询，而在**埋点规范**与**数据量控制**。

### 第四期：配置中心（自建）

策划表的下发、版本管理、灰度、回滚、热更。与第一期的玩家数据强耦合（灰度要按玩家分桶）。

## 关键约束（先写死，避免后期返工）

1. **客户端不可信。** 任何驱动发奖、扣费、进度的数据，必须由服务端计算或校验。Nakama 的 `storage` 允许客户端直写，这是能力也是坑，权限必须显式收紧。
2. **金额一律整数。** 货币用 int64 最小单位（分/厘），不使用浮点。Nakama 的 `wallet` 本身就是 `map[string]int64`。
3. **流水不可变。** 余额是快照，流水是账本；对账只信流水。
4. **配置与状态分离。** 策划表是配置，进度是状态；配置可回滚，状态只能补偿。
5. **分区键先行。** 事件类数据（对战、埋点）在建表时就确定分区与保留期，事后改造代价极高。
