# 02 · 能力差距矩阵

以 Nakama 为参照，逐项判断「复用 / 扩展 / 自建」。判断依据是**数据可信度要求与查询形态**，不是实现难度。

## 矩阵

| # | 能力 | Nakama 现状 | 判断 | 说明 |
|---|---|---|---|---|
| 1 | 账号与多渠道登录 | 内建（设备/邮箱/各平台） | 复用 | 模型可直接照搬 |
| 2 | 玩家档案（昵称/头像/设置） | `users` 强类型列 + `metadata` | 复用 | `metadata` 只放 <1KB 且每次登录必读的字段 |
| 3 | 货币与资产余额 | `wallet` = `map[string]int64` | 复用 + 扩展 | 需补上限约束、货币元数据（精度/展示名/是否可交易） |
| 4 | 资产流水与审计 | `wallet_ledger` | 复用 | 需补业务维度索引（订单号/活动 ID/来源） |
| 5 | 道具、卡牌、装备、背包 | **无** | 自建 | 基于 storage 一物一行；`write=0` |
| 6 | 排行榜 | `leaderboard`（cron 重置、多算子） | 复用 | 注意 `operator` 与 `sort_order` 语义 |
| 7 | 支付与对账 | `purchase`（transaction_id 主键） | 复用 | 天然幂等，重复回调不重复发货 |
| 8 | 站内信/邮件/补偿 | `notification`（code + content JSONB） | 复用 | 可挂附件发放 |
| 9 | 实时对战（房间/同步） | match handler + WebSocket | 复用 | 只解决「同步」，不解决「落库」 |
| 10 | 对战结果上报与结算 | **无**（对局内存态，不持久化） | 自建 | 见下节 |
| 11 | 关卡/行为分析 | **无** | 自建 | 见下节 |
| 12 | 配置中心 | **无**（仅 Console 的运行时配置） | 自建 | 见下节 |
| 13 | 定时调度/补偿任务 | 无公开 API（内核仅用于排行榜重置） | 自建 | 独立调度服务更可控 |
| 14 | 数据导出/离线分析 | 无 | 自建 | 需 CDC 或定时抽取 |

## 能力 10 · 对战数据上报

**Nakama 的边界：** match handler 只负责帧同步与状态广播，对局状态存在内存（match registry），服务端不落库、不做结算。所以「打完一局，写一条战绩」这件事必须自建。

**首先要决策的是权威模型，而非表结构：**

| 模型 | 做法 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| A 服务端权威结算 | 服务端跑完整战斗逻辑，客户端只上报输入 | 无作弊面 | 服务端算力成本高，战斗逻辑需双端一致 | 竞技、付费相关 |
| B 客户端上报 + 服务端校验 | 上传战斗录像/关键帧，服务端回放验证 | 算力成本低 | 校验逻辑复杂，漏判即漏洞 | 单局时长较长、算力敏感 |
| C 客户端上报 + 统计兜底 | 只做异常值检测（伤害上限、时长下限、数值突变） | 成本最低 | 只能用于分析，**不能驱动发奖** | 纯 PvE、休闲玩法 |

**建议：** 按玩法分档，不要全局一刀切。驱动发奖（金币、段位、抽卡券）的路径必须走 A 或 B；C 仅用于埋点分析。

**数据结构要点：**

- 主键用 `battle_id`（服务端下发，全局唯一），不要用客户端生成的时间戳
- 必须落 `server_seq` / `client_seq` 双序列，用于检测重放与乱序
- 分区键用 `battle_end_time`（按天/周分区），保留期在建表时定死
- 明细与汇总分离：`battle_record`（明细，短期）→ `battle_stat_daily`（预聚合，长期）

## 能力 11 · 关卡策略分析

**要解决的问题：** 玩家在第几关卡住、卡多久、卡点前后的行为序列、版本改动对通过率的影响。对标数数科技这类事件分析产品的能力面（漏斗、留存、分布、序列）。

**核心不是查询引擎，是事件模型与埋点治理：**

1. **统一事件模型**：`event_name` + `event_time` + `user_id` + `session_id` + `props(JSONB)`。所有分析都从这一张宽表出发，避免每来一个需求加一张表。
2. **埋点字典先行**：`event_name` / `prop_key` 必须有注册表（类型、枚举、单位、负责人），否则后期 props 会变成不可查询的垃圾场。这是这类系统 80% 的失败原因。
3. **两条链路分离**：
   - 实时链路（写入快、可丢、用于大盘与告警）
   - 离线链路（T+1 全量、用于漏斗与留存）
   混在一条链路里，会导致分析查询拖慢线上写入。
4. **关卡维度预聚合**：`stage_id` × `date` 的进入数、通过数、平均尝试次数、卡点分布。分析型查询不要直接扫明细。

**取舍：** 自建分析系统的工作量集中在「数据治理 + 预聚合」，不在前端。若公司已采购同类产品，建议先接入再自建，避免重复投入。

## 能力 12 · 配置中心

**Nakama 只有运行时配置**（启动参数 / Console 配置），没有「策划表」概念，`data/modules` 下也不存在配置下发机制。

**必须支持的能力：**

- 版本化：每次发布生成不可变版本号，可回滚
- 灰度：按 `user_id` 哈希分桶，而不是按百分比随机（同一玩家必须稳定命中）
- 热更：客户端运行中拉取新版本，无需重启
- 校验：发布前做 schema 校验与引用完整性校验（引用了不存在的道具 ID 直接拒绝发布）
- 审计：谁、何时、改了哪个字段、影响多少玩家

**与玩家数据的耦合点：** 灰度分桶依赖稳定的用户哈希，配置版本 ID 需要写进玩家存档（否则线上出现「同一玩家两次战斗用不同配置」的争议）。

## 优先级建议

按「依赖关系」而非「价值」排序：

1. 第一期玩家数据 → 是所有后续系统的地基（`user_id` 唯一性与存档模型）
2. 配置中心 → 关卡分析需要知道「当时用的哪版配置」，否则数据无法解释
3. 对战数据上报 → 分析链路的主要数据源
4. 关卡策略分析 → 消费前三者的产出

先做分析、后补配置，会导致历史数据永久失去配置上下文，这个教训代价很高。
