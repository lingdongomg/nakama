# 03 · 实现模式参考

把 Nakama 与 Hiro 中值得照搬的工程模式提炼成实现约定。与既有文档的分工：

- `01-nakama-baseline.md` 回答「Nakama 有什么、源码在哪」
- `02-gap-matrix.md` 回答「哪些复用、哪些自建」
- 本文回答「自建时按什么模式写」

每个模式只记三件事：**解决什么、关键约束、能不能搬**。不复述 API。

## 0. 模式总览

| # | 模式 | 一句话 | 对应 Nakama 实现 |
|---|---|---|---|
| P1 | 声明式权限 | 权限是数据字段，不是代码分支 | `storage.read` / `write` |
| P2 | 版本号乐观锁 | 不锁行也能防覆盖 | `version = md5(value)` |
| P3 | 三元组标识 | ID 由客户端算出，省一次往返 | `(collection, key, user_id)` |
| P4 | 奖励中心抽象 | 所有产出收敛成一个对象 | 无（Hiro 提供） |
| P5 | 延迟交付 | 邮箱做缓冲层 | `notification` |
| P6 | 乘数而非改配置 | 临时增益不碰全局数值 | 无（Hiro 提供） |
| P7 | 时间戳结算 | 不跑定时任务也算得出资源增长 | 无（Hiro 提供） |
| P8 | 派生索引 | 搜索与真相分离 | bluge 索引 |
| P9 | 事件驱动扩展 | 用 hook 而非轮询 | 运行时 hook |

## P1 · 声明式权限

**问题.** 权限判断散落在各 handler 里，没人说得清全貌，审计只能靠 grep。

**做法.** 权限成为数据对象的两个字段，取值受限枚举：

| 字段 | 0 | 1 | 2 |
|---|---|---|---|
| `read` | 仅服务端 | 仅所有者 | 任何人 |
| `write` | 仅服务端 | 所有者 | — |

服务端调用绕过全部权限，因为它是唯一可信方。客户端接口只做「检查权限 + 读写」，需要业务判断的操作一律推到 RPC。

**约束（三条都会踩）.**

1. **写入覆盖整个对象，包括权限。** 改 value 时不传权限，会被重置为默认值（Go 运行时为 `0`，TS/Lua 为 `1`）。保留原权限必须先读再原样回传。Nakama 的 `version` 与权限同属"整体覆盖"语义，处理方式一致。
2. **权限是对象级，不是字段级。** 同一对象里「公开昵称」与「私密邮箱」不能共存，需拆对象。
3. **默认值不等于安全值。** 01 第 5 节已记：把权威数值放进 `write=1` 的 collection 等于自毁防线。建 collection 时必须显式声明权限，不能依赖默认。

**检验标准.** 能不能用一条 SQL 查出「所有公开可读的数据」。能，说明建模成功；不能，说明权限被埋进逻辑里了。

## P2 · 版本号乐观锁

**问题.** 两个请求同时改同一条数据，后写的静默覆盖先写的，双方都不知道。

**做法.** 每次成功写入返回 `version`，下次写入时带上，不匹配则拒绝。三种用法对应三种语义：

| 传什么 | 语义 | 场景 |
|---|---|---|
| 具体版本号 | 条件更新（CAS） | 读-改-写，防丢失更新 |
| `"*"` | 仅当不存在时创建 | 幂等初始化、抢占式领奖、分布式锁 |
| 不传 | 无条件覆盖 | 心跳、可容忍覆盖的状态同步 |

**为什么不用行锁.** Nakama 内部两种都用了，分界很清楚：

- `wallet` 用 `SELECT ... FOR UPDATE` 锁整行（`server/core_wallet.go:126`），因为余额是**单行、高频、强一致**的数值，必须串行化。
- `storage` 用 `version = md5(value)` 做 OCC（`core_storage.go:785`），因为文档是**读多写少、按对象隔离**的，行锁会让并发度崩掉。

**结论：数值型余额用行锁，文档型数据用 OCC。** 不要反过来，也不要在文档上套行锁。

**约束.**

1. **冲突是对象级，不是字段级。** 两个请求改同一对象的不同字段一样冲突。这是「按更新频率拆分对象」的唯一理由：高频变化的位置、余额、经验不要和低频变化的解锁列表塞进一个 JSON。
2. **批量写必须单事务。** Nakama 的 `MultiUpdate`（`server/core_multi.go:27`）把账户、storage、wallet 放进同一个 pgx 事务，任一失败整体回滚。01 第 6 节已指出这是最值得借鉴的一处设计，自建系统必须保留这个语义。
3. **重试要基于新读到的值。** 拿着第一次读的旧值重试，重试多少次都是错的。

## P3 · 三元组标识

**做法.** 用 `(所有者, 集合, 键)` 定位对象，不引入自增 ID。所有者留空表示全局对象。

**收益.** 客户端能自己算出要读的 ID，省一次「查 ID」的往返；写同一个键天然是覆盖，天然幂等。

**什么时候不该用.**

- ID 必须由服务端生成时（订单号、对战 ID、房间号），硬套会引入可猜测性问题
- 需要跨对象事务或关联查询时，键值模型会逼你在应用层做 join

**约束.** 键一旦语义化就不好改。版本信息放 value 里，不要塞进键名（`save_v2` 会导致迁移时新旧两个键共存）。

## P4 · 奖励中心抽象

**问题.** 成就、任务、活动、商店、广告、客服补偿、赛季结算，每个都要发东西。各写一套的结果是：发放逻辑重复、幂等各做各的、出纠纷查不到来源。

**做法.** 定义一个 Reward 对象，所有系统的产出一律表达成它。四个正交维度：

| 维度 | 取值 |
|---|---|
| 内容 | 货币 / 道具 / 体力 / 修正器 / 组合 |
| 规则 | 必定发放 / 按权重抽取 / 延迟发放 / 临时倍率 |
| 目标 | 本人 / 邮箱 / 队伍 / 队员 |
| 幂等 | 由「来源 + 业务键」唯一约束保证 |

**约束.**

1. **幂等键必须能从业务推导，不能用随机 UUID。** `daily_login_2026-10-28` 是对的；`uuid4()` 等于没有幂等，同一天点十次发十份。
2. **发放记录存快照，不存引用。** 只存 `reward_id` 的话，三个月后策划把奖励从 100 改成 50，玩家来领时拿到 50，而当时页面承诺 100。把发放那一刻的实际内容序列化存下来。
3. **调用方不允许直接改钱包。** 所有发放走同一个 `grant()`，否则流水、审计、补发、退款全部失效。

**优先级.** 这是整套模式里投入产出比最高的一个：把「发东西」从 N 处实现收敛到 1 处。

## P5 · 延迟交付

**问题.** 活动结束要同时给几万人发奖，同步发会超时、会打爆库；玩家离线时发的奖励会丢；发放中途失败没有重试余地。

**做法.** 奖励不直接入账，先落一条待领取记录，玩家上线后主动领。

```
pending ──领取──▶ claimed
   │
   └──过期──▶ expired
```

一次解决四件事：离线投递、批量异步、失败重试、发奖留痕。

**约束.**

1. **领取必须幂等。** 连点两次、超时重试都不能发两份。靠 `(user_id, grant_id)` 唯一约束加事务保证，不靠客户端「只点一次」。
2. **必须有过期时间。** 无过期的邮箱表会无限增长，且几年后玩家回来领一批上古奖励会直接冲击经济。
3. **顺序是先落库再发放。** 反过来做（先加钱再写记录），中间崩溃就产生「钱到了但查不到来源」的账。

**阈值.** 一次要发超过几百份的奖励，一律走邮箱，不要同步直发。

## P6 · 乘数而非改配置

**问题.** 做「看广告得双倍金币，持续 30 分钟」。改全局配置会影响所有人、难回滚，也无法只给看广告的人。

**做法.** 不动配置，给玩家挂一条带过期时间的修正器，结算时相乘。

```
final = base × ∏(active_modifiers[kind].value)
```

**约束.**

1. **必须有上限。** 广告 2× 叠活动 2× 叠 VIP 1.5× 就是 6×，再来个节日 3× 就是 18×。要么限制同时生效条数，要么给总倍率设天花板。
2. **按来源打标签。** 不标来源，做不了「这个活动送出去多少」的结算，出问题时也无法只回滚单一来源。
3. **存绝对过期时间，不存剩余秒数。** 存剩余秒数则每次读都要写回扣减，读写放大且并发不安全。

**附带收益.** 天然支持 A/B——给实验组挂修正器即可，不动配置。

## P7 · 时间戳结算

**问题.** 体力恢复、离线收益、建造队列。起定时任务每秒扫描百万玩家，成本随用户数线性增长。

**做法.** 不主动计算，只在读取时按时间差反推。

```
elapsed = now - last_settled_at
ticks   = floor(elapsed / interval)
gain    = min(cap - current, ticks)
current = current + gain
last_settled_at = last_settled_at + gain × interval   ← 只推进整数周期
```

**约束.**

1. **余数必须保留。** 写成 `last_settled_at = now` 会抹掉不足一个周期的时间，玩家反复刷新反而恢复更慢。这是这类系统最经典的 bug。
2. **只用服务端时间。** 客户端时间可改，用它算等于让玩家自己发资源。
3. **上限在结算时拦。** 否则离线一年回来，体力溢出成天文数字。

**成本.** O(1)，与玩家数无关，不跑任何后台任务。所有「随时间线性增长」的量都适用：体力、离线收益、建造队列、技能冷却、每日重置。

---

## P8 · 派生索引

**问题.** 要跨用户查询「段位 > 10 且地区是欧洲的玩家」，逐个读存档再过滤不可行。

**做法.** 主存储之外维护一份派生搜索索引：写入时异步更新，查询走索引，命中后回表取完整数据。索引只含显式声明的顶层字段。

**约束.**

1. **索引有硬上限。** 是有界结构，超限淘汰最旧条目。「索引里没有」不等于「数据不存在」。当完整表用，数据量上来后会静默丢结果。
2. **最终一致。** 刚写完可能几毫秒后才可见；更麻烦的是查询可能返回**已不满足条件**的旧条目。凡「过滤条件必须严格成立」的场景（发奖名单、结算名单），拿到结果必须逐条复核。
3. **回表有开销。** 某些实现提供「只读索引不回表」的加速模式，代价是返回对象只有被索引的那几个字段，调用方会误以为数据缺失。

**判断标准.** 「用来搜的」和「用来信的」必须是两个东西。排行榜内存排名是搜索，库里的分数记录才是真相。数据量超过内存时就换真正的搜索引擎，不要在有界索引上硬撑。

## P9 · 事件驱动扩展

**问题.** 想在「注册成功后发欢迎邮件」「写排行榜后同步运营后台」「提交匹配前校验封禁」处插入逻辑。改框架源码是最差解。

**做法.** 在内建操作前后暴露钩子，按消息名注册。

| 类型 | 时机 | 能力 |
|---|---|---|
| before | 操作执行前 | **可修改请求内容**，也可直接拒绝 |
| after | 操作成功后 | 做副作用 |
| 事件钩子 | 匹配成功、榜单重置、赛季结束、进程关闭 | 离散事件处理 |

**约束.**

1. **before 是最高效的防作弊位。** 客户端提交「我的段位是 50」，在 before 里改写成服务端记录的真实段位，后续所有逻辑都拿不到假数据。这比在每个业务函数里校验可靠得多。
2. **after 失败不应影响主流程。** 发通知失败不能让「写存档」回滚。副作用要能容忍失败或进队列重试。
3. **钩子里不做重活。** 它跑在请求路径上，直接叠加到玩家延迟。

**更重要的反面经验：不要用定时任务实现时间逻辑。** 多节点部署时每个节点都跑一份，逻辑重复执行；还会对全体离线玩家做无用功。改成事件驱动——玩家回来时调一个 RPC，在里面对他一个人补算（即 P7）。

## 反模式清单

设计评审时逐条对照。

| 反模式 | 后果 | 替代做法 |
|---|---|---|
| 一个部署承载多款游戏 | 一款做活动打满 CPU，全部游戏一起卡；库故障全系停服 | 一游戏一部署，共享中心身份服务 |
| 用业务库存埋点 | 键值模型无聚合能力，每条事件一次库往返 | 独立分析链路，见 `04-liveops-model.md` |
| 用业务库做配置中心 | 读放大，把最大 QPS 花在最不该花的地方 | 版本化配置表 + 客户端缓存 |
| 建自定义表、写自定义 SQL | 破坏升级路径，拿不到权限/版本/索引内建能力 | 用集合 + 键 + JSON，必要时加索引 |
| 用定时任务实现时间逻辑 | 多节点重复执行，扫全量离线玩家 | P7 时间戳结算 |
| 整个存档塞一个对象频繁写 | 版本冲突暴涨，几乎每次写入都要重试 | 按更新频率拆对象 |
| 对局状态当持久状态用 | 节点重启即丢，一次发布作废所有进行中对局 | 明确快照策略，或文案上接受作废 |
| 用排行榜做数据分析 | 内存结构、重启重建，查不出「昨天多少人到第 10 关」 | 排行榜只做展示，分析走数仓 |
| 权限依赖默认值 | 权威数值落进 `write=1` 的 collection | 建 collection 时显式声明权限 |

## 落地检查清单

新建一张表或一个模块时，过一遍：

- [ ] 权限是否显式声明？有没有依赖默认值？
- [ ] 并发写用行锁还是 OCC？判断依据是数值型还是文档型？
- [ ] 需要跨对象一致性的操作，是否在同一个事务里？
- [ ] 所有发给玩家的东西，是否都走了同一个 `grant()`？
- [ ] 幂等键能否从业务推导出来？不是随机 UUID？
- [ ] 发放记录存的是快照还是引用？
- [ ] 有时间增长的量，是否用时间戳结算而非定时任务？
- [ ] 临时增益是否用修正器，而不是改全局配置？
- [ ] 用索引查出来的结果，在驱动发奖/结算前是否复核过？
- [ ] 有没有把「多节点会重复执行」的逻辑写成定时任务？

## 与 Nakama 的实际差异（自建时注意）

| 项 | Nakama 行为 | 自建时的选择 |
|---|---|---|
| 默认权限 | `storage` 默认 `read=1` `write=1`（Go 运行时写为 0） | 统一默认 `write=0`，显式放开 |
| `metadata` 更新 | 整体覆盖，不合并（`core_account.go:373-376`） | 与 `wallet` 的 `\|\|` 合并语义统一，或强制读-改-写 |
| 钱包上限 | 只有非负校验，无上限（`core_wallet.go:191-199`） | 补每货币上限与总资产上限，防通胀 |
| 索引一致性 | 最终一致，有 `maxEntries` | 结算类查询不要依赖索引 |
| 多游戏隔离 | 不支持，设计上一部署一游戏 | 需要多租户就自己在 `user_id` 之外加 `app_id` 维度 |
